Content Safety Sandbox

Positioning

One workbench, three evaluation paradigms

An LLM-powered content-safety evaluation workbench that unifies three evaluation paradigms — risk detection, red/blue adversarial testing, and LLM-as-a-Judge scoring — into one surface, with live streamed reasoning traces.

Product thinking

Four decisions that shaped the build

01 · Make reasoning a first-class citizen

Most moderation tools are black boxes: submit text, get a pass or block. But safety needs explainability — you cannot improve or audit a guardrail you cannot read. The core decision was to stream the model's reasoning live, paired with a workflow node graph that advances with the process, turning an invisible pipeline into something readable and auditable. A detector becomes an interpreter and an auditor.

02 · Three flows are a maturity model

Flow 1 detects: is this content safe? — for triage. Flow 2 attacks: can an adversary breach my guardrail? — active and adversarial, the proof that safety is not static. Flow 3 judges: how safe is my model overall? — meta-evaluation against a rubric, the strategic layer. Together they form a detect → attack → assess progression that mirrors a real security team's lifecycle. This is deliberate information architecture, not feature stacking.

03 · Design language is persona positioning

SOC (security operations center) plus a minimal lab aesthetic, deep indigo as the primary, with pass-green / block-red / running-amber status colors — this speaks to the security and risk professional persona, not the ordinary consumer. The visuals are the positioning.

04 · Streaming is a control plane

Typewriter-style live rendering is not only decorative: it lets the evaluator interrupt the model mid-decision through AbortController. That itself is a cost-control mechanism — killing a runaway generation early saves tokens. So the streaming that seems to add token cost is really part of the product's control plane.

The problem

The safety question is larger than detecting a keyword.

What a single check misses

Role-play jailbreaks, encoded prompts, multi-step inducement, partial leakage, and over-refusal all fail in different ways.

The product question

How can these failure modes be organized into a repeatable workflow that makes responsibility, evidence, and uncertainty easier to inspect?

Product planning

Three flows, each responsible for a different layer.

Flow 1 · Input safety

Jailbreak prompt test

Parse the prompt, scan for risk, classify it, and return an assessment.

Flow 2 · Defense behavior

Red-blue adversarial test

Compare a red-team attack against an explicit blue-team guardrail and produce a verdict.

Flow 3 · Output safety

LLM-as-a-Judge

Parse the content and rubric, score dimensions, calibrate, and generate a report.

Architecture boundary: the three flows form a conceptual progression from request boundary to final answer. The current interface exposes them as selectable workflows; it does not prove that every request runs through all three in sequence.

Key takeaway · The latency pick

Model A holds an 85% block rate with zero false positives at 1416 ms — roughly 40% faster than B and C — the default choice for real-time guardrails.

Key takeaway · The strictness pick

B and C trade speed for slightly tighter blocking (88% / 85% at about 2.2 s), a fit for compliance-heavy review; D's 8.8 s latency reserves it for offline screening.

Cost boundary: boundary positives reach the LLM judge only when the target model refuses — lazy arbitration keeps judge tokens proportional to refusals, not to traffic.

Intelligent analysis

Failures stop being a red badge — they become root causes and patches.

01.Read the failure, not just the badge

A bare “Failed” state hides the root cause. The analysis agent parses run logs and clusters misses by semantic vector instead of test ID, so the fence's real weak spots surface first.

DAN Role-PlayPII & Privacy ExtractionPrefix OverrideHypothetical ScenarioMultilingual Confusion
02.Close the loop: patches in, experts in

Generated mitigation fixes

The advisor turns each cluster into a layered patch — regex pre-filters, system-prompt overrides, and output-classifier thresholds — plus a weekly adversarial re-test cadence.

Human-in-the-loop flywheel

One-click expert review on any flagged case; confirmed corrections are formatted into the golden dataset that anchors future fine-tuning and alignment.

Key takeaway · Constraint beats autonomy

Dynamic planners and live red/blue agent debates were cut on purpose: evaluation runs on a deterministic five-step pipeline, and analysis happens after the run, where every step stays traceable.

Key takeaway · The 85% lesson

A high block rate looked great until the misses were read — DAN role-play and PII extraction made up 36% of failures, and chasing the rate had begun to over-block normal requests.

Product thinking & lessons

From building fast to proving reliable — what an LLM red-blue sandbox changed about how I think of risk decisions.

01.From Hard-Coded Rules to Natural Language Strategies

GenAI Safety Sandbox

—The Pivot · A Reality Check
"

I initially thought the value was speed of prototyping. But after adversarial testing, I realized the real challenge is production-grade reliability.

Field note · after the first adversarial test round

Non-Deterministic Boundary Shift

Tweaking a few prompt words can unintentionally alter decision boundaries, boosting recall while spiking false positives.

Probabilistic Evaluators

Using LLMs as safety judges means relying on another probabilistic model that requires its own validation layer.

02.The Expanding Release Surface
Traditional Risk Release2 components
Model package Fixed threshold
GenAI Risk Release6 components
Model version System prompt Guardrails Eval dataset Judge rubrics Fallback rules

The release surface tripled: every strategy tweak now ships as a versioned set of artifacts that must be tested together.

Key takeaway · The trade-off

Building a risk decision system now takes minutes — proving it won't fail unpredictably takes weeks.

Key takeaway · The metric

Prompting makes strategy cheap; making it traceable, measurable, and reliable remains hard.

Build story

From a mock UI to a live LLM backend

V1 · Mock-first validation

Pure frontend with mock data and a Chinese UI. The goal was to validate the interaction model, design language, and three-flow information architecture first — deliberately decoupled from backend readiness, so expensive real infrastructure would not be layered onto the wrong UI.

V2 · Real LLM over SSE

Switched to real LLM calls, a fully English UI, and SSE streaming. English targets a global AI-safety audience and performs more stably on safety tasks; SSE fits the strictly one-way server→client stream natively over HTTP with simple deployment, whereas WebSocket's bidirectional capability was unused.

Tech stack

Next.js 16 (App Router) React 19 TypeScript 5 shadcn/ui Tailwind CSS 4 SSE streaming coze-coding-dev-sdk

Next iteration

Make the evaluation itself easier to trust.

Clarify label semantics

Separate topic risk, output-safety verdict, and safety-quality score so that labels cannot appear contradictory.

Create comparable records

Store model, policy version, timestamp, expected label, actual verdict, repeat count, and FP/FN definitions. Batch execution, live backend traces, judge calibration, and repeated-run consistency.

Calibrate the judge

Use reference labels, human review, repeated trials, and disagreement analysis before trusting aggregate scores.

Extend the workflow

Prototype routing, multi-model comparison, and adversarial loops only after the evidence model is stable.

Reflection: the useful product move was not adding three tabs. It was separating input risk, defense behavior, and output quality into distinct evaluation responsibilities.

Observed friction

Four visible problems pointed to one structural mismatch.

Visual trust

The main control’s shadow looked like a second, misaligned rectangle.

Gesture trust

A long-press drag could still trigger the button action on release.

Spatial continuity

A three-card carousel exposed gaps and ghosting during faster movement.

Feedback coherence

Sound, haptics, animation, and state changes did not yet form one system.

Root cause: the first version treated a static three-card layout as a continuous interaction control. Parameter tuning could reduce symptoms, but it could not resolve the model conflict.

Product decisions

Let the visual hierarchy change with the user’s task.

StateCard treatmentInteraction ruleUser value
IdleFocused day is largeTap-to-light is enabledPreserves the primary action
DraggingAll days become compactButton action is suppressedPrevents reflow and accidental logging
MomentumAll days stay compactMove 1–5 days step by stepSupports speed without losing orientation
SettlingFocused day expands againUnlock after spring settlingReturns to a stable logging state

Development process

Move from visible fixes to one coherent interaction model.

01

Visual structure

Replace an out-of-bounds shadow with a real depth layer.

02

Gesture correctness

Track dragging and momentum explicitly.

03

Continuity

Render a ±7-day buffer around the focus.

04

Stable layout

Keep cards compact while moving.

05

Feedback system

Align sound, haptics, and animation with real state changes.

Before / after

Dimension1.01.1User value
Date bufferPrevious / current / next±7 days around focusFast movement no longer exposes gaps
Single gestureUsually one dayMomentum across 1–5 daysHistorical browsing becomes faster

Verification

Turn subjective experience into regressions that can be tested.

Representative UI tests

  • A normal tap still lights the selected day.
  • A long-press drag changes date without lighting the pressed day.
  • A fast swipe can cross multiple days and settle.
  • Current-month navigation state is visually and functionally consistent.

Why device UAT still matters

  • Gesture friction and movement speed
  • Sound and haptic timing
  • Reduce Motion behavior
  • Different physical screen sizes

Reflection and next iteration

Correctness comes before decorative polish.

Momentum usability

Observe whether people frequently overshoot before changing the 1–5-day model.

Accessibility

Run dedicated VoiceOver, Dynamic Type, contrast, and Reduce Motion checks.

Data and privacy

If analytics are introduced, revisit the local-first promise and App Privacy before implementation.

Core learning: accidental logging is a correctness problem, not a small UI defect. Structural interaction problems need a structural solution—not another threshold adjustment.
